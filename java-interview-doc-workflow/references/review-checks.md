# 1 单篇面试文档复核步骤

## 1.1 复核范围

- 逐节检查全文，包括正文、附表、示例、代码、引用和待确认事项等实际包含的内容。

- 复核答题文档时，检查回答是否覆盖已确认的考点，面试口述与详细方案（如有）是否一致，以及技术来源是否支持文中的结论。

- 复核汇总文档时，检查应汇总的内容是否齐全，所列结论是否与对应文档的最新结论一致。

- 复核导航文档时，逐题核对答题范围、候选理由和对应的答题文档链接。

## 1.2 复核步骤

### 1.2.1 执行复核并处理发现的问题

1. 每轮复核都应检查技术内容、表达、文档结构及相关引用是否符合本技能的要求。

2. 每次修改后，应对照修改前后的内容，逐项核对本次要求是否完整、准确地落实，并检查实际改动是否都在授权范围内。

3. 复核“已确认规则”章节时，应逐项对照用户已确认的要求，检查是否有遗漏，以及记录是否准确保留了要求的原意和适用范围。未经用户确认的建议、推测或未验证的结果，不能写成用户已确认的要求。

4. 复核发现的问题可以直接修正时，应修改对应正文；需要补充信息、验证或存在异议时，应按本技能的对应规则记录和处理。

5. 修正本轮发现的问题后，重新检查受影响的内容。

6. 技术问题尚未解决或仍需用户决定时，不能只修改措辞，就将问题视为已解决。

7. 复核时，已符合本技能要求的内容应保留原文。

### 1.2.2 复核面试口述版本

1. 对照「问题」章节中的题目，检查口述是否直接回答了面试官的问题。

2. 对照本题列出的考点，逐项检查每个考点是否讲清。

3. 答题范围另行指定了适用场景时，检查口述是否覆盖这些场景。

4. 答题范围限定了回答深度时，检查对应考点是否讲到要求的程度。

5. 对照项目材料，检查口述对项目做法的描述是否准确。

6. 涉及条件判断时，检查是否讲清根据什么作出判断。

7. 判断结果会改变处理方式时，检查是否讲清每种结果对应的处理动作。

8. 解释方案选择时，检查是否交代了听者理解选择理由所需的业务规则。

9. 从未参与项目讨论的听者角度通读口述。理解结论必须借助详细方案中的某段说明时，将必要内容补入口述的对应位置。

10. 复核面试口述版时，对照题目和本篇已确认的考点逐段检查。如果删去整段或其中某个细节后，听者仍能仅凭口述准确、完整地回答题目，且每个考点的作答要求都已满足，就删去这部分内容。

   核心考点涉及具体实现时，保留讲清该考点所需的关键代码或配置，以及对应的注释或设置理由。

   **示例** 题目问“为什么批次状态更新和任务初始化必须在同一个事务中”，口述应讲清按批次状态决定是否初始化、分别提交的风险，以及一起提交或完整回滚的结果。Redis 启动锁、唯一键设计和故障恢复的细节可以在详细方案中说明。

11. 复核面试口述版时，应检查各要点的划分是否清楚，讲述顺序是否便于听者理解。

12. 复核面试口述版中的操作说明时，应检查是否讲清操作对象、具体做法和结果。存在并列操作时，应逐项检查动作是否明确；只写了数据名称、状态值或处理结果时，应补全对应动作。“处理”“同步”等概括性表述未讲清具体做法，且理解回答需要这些信息时，应在原句中补充说明。

13. 复核口述中的流程说明时，按实际执行顺序检查以下内容。

   - **怎样开始** 流程由什么事件触发？开始前要满足哪些条件？

   - **怎样进入下一步** 说明开始下一步需要满足什么条件。多个请求都可能执行同一操作时，讲清当前请求根据什么结果判断自己可以继续。条件只适用于首次启动、暂停后恢复等特定场景时，直接写明场景名称。检查开始下一步所需的条件是否写在该步骤前。复核功能总述时，如果后一步依赖前一步留下的消息、任务或状态，检查口述是否讲清谁留下了什么、后一步由谁在什么时候使用它，以及这样解决了什么问题。

   - **状态变化后怎样处理** 流程涉及状态变化时，检查口述是否讲清这次变化会怎样影响后续处理。

   - **哪些写入要一起提交** 流程依赖多项写入一起提交时，检查口述是否明确指出哪些操作在同一个事务中完成。

   - **怎样判断流程结束** 检查口述是否讲清流程结束的条件。

   **示例** 首次启动时，实例尝试把该批次的状态从“未启动”改为“运行中”。只有这次更新命中一行，它才在同一事务里保存扫描范围并创建任务。实例确认自己的事务提交成功后，才派发任务。

14. 复核面试口述版中的因果表述时，应检查因果关系是否有依据，以及文中交代的条件和做法是否足以产生所述结果。涉及异常后果时，应检查“异常发生后留下的结果→后续流程的判断或操作→最终影响”是否完整、准确；存在缺失环节时，应补充理解结论所必需的说明。结论还依赖其他条件或机制时，应在对应内容旁说明。

15. 复核或补充某个段落时，应同时检查前后相关段落，明确各段分别说明什么。发现理由不充分时，先判断是必要解释缺失，还是结论出现过早；解释缺失时补充，后文已有完整解释时优先调整结论的位置或删除提前重复的结论，不把后文的整套解释复制到当前段落。合并重复说明时，应保留各处不同的条件和限制。

   **示例** 三个相邻小节分别说明“初始化的判断依据”“分别提交的风险”“同一事务的作用”时，第一节只需讲清初始化条件，不必提前加入“因此必须使用同一事务”的结论，也不必复制后两节的风险和解决方式。

16. 复核面试口述版时，如果简称、对象指代或技术用语容易让听者产生误解，应改写相关表述，并补足理解这句话所需的信息。

17. 单独通读口述版，逐个核对其中的数值参数。每提到一个具体取值，都要让听者知道这个数表示什么、为什么这样取。项目材料只给出数值时，就在口述中注明「取值依据待确认」。示例值或建议压测值也要在口述中标明。

18. 题目要求判断参数取值是否合理时，先从项目材料中找出影响判断的数据。能用这些数据算出实际工作量或任务数时，在口述中给出计算过程和结果。

19. 结合计算结果和项目的运行条件，说明这个取值是否合适。材料不足时，写清缺少哪项数据，以及缺少它会影响哪个判断。

### 1.2.3 复核考点和回答

1. 复核时发现考点可能遗漏、重复或答题范围需要调整，应说明具体问题和依据，并提交调整建议。用户确认调整考点后，更新导航中的对应条目和受影响的答题文档。

2. 答题文档设有「详细方案」时，检查其中是否具体说明了需要进一步解释的内容。

3. 答题文档设有「详细方案」时，对照面试口述版与详细方案中讲解同一事项的内容，检查两处的结论、成立条件、适用范围，以及方案确认、功能实现和效果验证的状态是否一致。

4. 复核同一机制的多道已确认考点时，按「已确认考点」导航逐题打开对应的答题文档，核对该篇口述是否完整回答本题。每篇以本题已确认的答题范围为准。

   **示例** 批次启动锁涉及三道已确认的题。《批次启动锁设计》讲清哪些请求竞争同一把锁、何时加锁和释放锁。《分布式锁选型》讲清项目需要哪些锁能力，以及 `RLock` 如何满足这些要求。《多实例启动互斥》讲清租约提前到期后，系统如何避免同一批次被重复派发。复核时分别到这三篇检查对应的答案。

5. 复核机制类答案时，核对正文是否讲清该机制保护哪些操作，以及保护范围在哪里结束。正文写错保护范围时，依据项目材料修正。发现关键考点遗漏，或多个考点混在一起、需要调整已确认的答题范围时，按[提交考点调整建议](/C:/Users/Administrator/.codex/skills/java-interview-doc-workflow/references/review-checks.md:91)提交调整建议。

   **示例** 如果口述版写成“启动锁保证任务不会重复派发”，应检查任务派发是否发生在锁释放之后。若派发不在锁内，就应改为“启动锁保护状态处理和任务准备，任务派发需要另行说明幂等或重复控制”。

6. 复核功能总述时，先读主问题，再逐项检查总述考点。如果去掉某个考点，主问题仍能答完整，而这个考点实际回答的是一道独立追问，就提出调整建议。涉及已确认的考点或答题范围时，先请用户确认，再更新导航和答题文档。检查功能总述是否保留了理解主问题答案所必需的内容，以及只用于回答某道已确认独立追问的内容是否放在该追问的答题文档中。

7. 复核已有题目时，检查面试官能否根据提问前已经了解的信息提出这个问题，以及题干是否覆盖已确认的答题范围。如果题干预设了候选人尚未介绍的做法，或遗漏了必答内容，指出有问题的措辞，并给出与已确认范围一致的问法。建议调整答题范围时，将调整后的题目和范围一起提交用户确认。

### 1.2.4 核对技术结论、来源和状态

1. 复核时发现技术疑点，应根据可靠资料或实际验证结果重新核实相关结论。原文曾通过复核，不能作为本次疑点已解决的依据。

2. 复核技术结论时，应依据可核实的资料或验证结果，检查结论的适用范围是否准确，以及方案确认、功能实现和效果验证的状态是否如实表述。结论依赖特定条件时，应检查正文是否写明这些条件。

3. 复核文档中的示例时，应检查读者能否分辨哪些做法、参数或结果仅用于举例，哪些是项目实际采用的做法、配置或已验证的结果。

4. 复核文档中的引用时，应查阅所引资料，核对资料是否支持正文中的对应结论。暂时无法查阅资料，或无法判断资料是否支持结论时，应标明“来源待确认”，并说明哪些结论受影响。

5. 复核参数设置时，检查文档是否讲清参数控制什么、在什么条件下适用、取值或范围是多少，以及为什么这样设置。按[数值参数的单位要求](/C:/Users/Administrator/.codex/skills/java-interview-doc-workflow/references/document-writing-rules.md:175)检查是否注明了准确理解数值所需的单位。

6. 参数会动态调整时，检查文档是否讲清参数值怎样确定，以及什么条件会触发调整。

7. 复核项目参数时，检查文档是否说明该参数的用途，包括它作用于什么对象、控制什么行为。即使文档只给出参考值、示例值或建议压测值，也要讲清参数的用途。

   - 项目实际取值尚未核实时，注明「实际取值待确认」。

   - 取值已确认、理由尚未核实时，保留已确认的取值，并注明「取值依据待确认」。

8. 复核技术表述时，应核对句子实际表达的含义是否与依据一致，包括执行主体、动作、对象及组件之间的关系。不能仅因术语正确、句子通顺或相关源码已查阅，就认定表述准确；措辞使读者得出错误技术理解时，应直接修正原句。

   **示例** 源码表明 Redisson 已提供分布式锁实现，而正文写成“用 Redisson 封装这些机制”，容易让读者误以为需要自行封装。复核时，即使已查阅源码，也应将原句改为“使用 Redisson 提供的分布式锁”，使正文准确表达调用已有能力这一事实。

### 1.2.5 检查结构、导航和关联内容

1. 复核文档时，若有适用于全文的技术栈版本需要说明，应检查这些版本是否集中写在一级标题之后、“问题”章节之前的“说明”章节中。

2. 复核文档结构时，按[1.2.1 安排文档章节](/C:/Users/Administrator/.codex/skills/java-interview-doc-workflow/references/interview-document-writing.md:29)检查文档的一级标题，以及现有章节是否符合文档用途、当前问题和已有材料。答题文档还应核对所保留章节的相对顺序。

3. 复核标题时，检查一级标题是否与去掉 `.md` 扩展名的完整文件名一致。逐级核对二级及以下标题的章节归属、编号层级和同级编号的连续性。

4. 对照导航中本题的条目，检查答题文档「问题」章节是否保留全部内容和原有顺序，并按[整理问题](/C:/Users/Administrator/.codex/skills/java-interview-doc-workflow/references/interview-document-writing.md:53)检查小标题和考点编号。

5. 核对功能总述中的追问链接。段末链接应指向该段所讲考点的具体内容，文末「相关追问」中的链接应指向对应的答题文档。追问只在文末列出时，直接核对链接即可。

6. 复核详细方案导航时，应检查面试口述版中需要导航的结论是否附有链接，并逐一核对链接格式、目标路径和定位行号。链接文字应与目标内容一致，定位行号应指向对应内容的起始位置。文档调整后，应重新核对受影响的链接。

7. 复核导航时，应在 Codex 阅读器中逐一点击面试口述版的详细方案链接，确认是否跳到对应内容。未实际点击验证的链接，应说明其跳转效果尚未验证。

8. 每次修改文档内容后，检查本次改动是否影响同一文档的其他章节或关联文档。位于其他目录的关联文档也应纳入检查。

9. 发现受影响的内容时，在授权范围内同步修改。需要调整授权范围之外的内容时，说明具体影响并提交用户确认。

10. 提交前，逐篇检查本次新建或重命名的 Markdown 文档。文件名应以三位数字和下划线开头，一级标题应与去掉 `.md` 后的文件名一致。

11. 提交前，检查本次新建或重命名的 Markdown 文档所在目录的编号是否连续、有无重号。编号冲突和 `999` 文档按[1.2.1 确定文档顺序和编号](/C:/Users/Administrator/.codex/skills/java-interview-doc-workflow/references/document-restructure.md:67)处理。

12. 逐一检查本次改动影响的链接，确认每个链接都指向预期的文档或具体位置。

13. 提交前，对照最终文档清单和[配套文档命名规则](/C:/Users/Administrator/.codex/skills/java-interview-doc-workflow/references/document-restructure.md:103)，核对实际目录中的四类配套文档是否各只保留最新一份，并检查文件名、排列顺序和编号是否正确。
