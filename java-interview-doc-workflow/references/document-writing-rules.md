# 1 文档编写要求

## 1.1 正文表达要求

所有正文都应阐述有条理、逻辑层层递进、表述易于理解。

### 1.1.1 内容组织

#### 1.1.1.1 安排内容展开顺序

1. 根据内容之间的逻辑关系安排讲解顺序，不为套用固定结构打乱必要的前后依赖。

2. 理解某项内容需要先了解其他概念或规则时，应先解释这些概念或规则。

3. 说明执行过程时，应按实际执行顺序展开。

#### 1.1.1.2 说明的位置

1. 条件、原因、结果、限制及必要解释应放在对应内容旁，避免读者来回查找。

   **示例** 说明何时开启启动事务时，把抢锁结果和后续动作放在一起：“实例按批次 ID 构造锁键并尝试加锁。抢锁失败就结束本次请求。取得锁后，才开启数据库事务。”

### 1.1.2 长句拆分

1. 一句话包含多层意思、影响理解时，应按含义拆成几句，并保留必要条件和逻辑关系。

### 1.1.3 术语使用

1. 使用常规术语，不要自行造词。

2. 如果理解当前内容需要了解某个术语，应在该术语首次出现时解释其含义。

### 1.1.4 操作说明

1. 描述操作时，应说明由谁执行、处理什么对象、具体做什么，以及直接产生什么结果。并列说明多项操作时，每一项都应写清动作和对象，不能只列出数据名称、状态值或处理结果，让读者自行补全操作。

   **示例** 说明事务包含哪些操作时，应写“保存扫描上下界、初始化任务清单，并将批次状态改为‘运行中’”，而不是只列出“扫描上下界、任务清单和‘运行中’状态”。

2. 描述判断、计算、分类或选择操作时，应说明采用的条件、公式或其他处理规则。

   **示例** 计算消费记录的分片编号时，对商户号 `merchantNo` 进行哈希，再按物理分片总数取模。

3. 使用“处理”“同步”“初始化”等概括性表述时，应结合当前句及上下文，判断是否已说明具体执行的操作；未说明清楚时，再补充必要解释。

   **示例** 不能只说“将消费记录同步到 ES”，可以具体说明：ES 写入服务根据消费记录不可变的原始 `create_time` 确定所属月份的物理索引，再使用 Index API 将记录写入该索引。

4. 描述技术能力的提供和使用时，应准确区分由哪个组件实现、由谁调用，以及哪些部分需要自行开发，不能将调用已有能力写成自行实现或封装该能力。

   **示例** 使用 Redisson 已提供的分布式锁时，应写“使用 Redisson 提供的分布式锁”，不能写成“用 Redisson 封装这些机制”，让读者误以为需要自行实现相关机制。

### 1.1.5 流程说明

1. 介绍机制或流程时，应说明其用途。

   **示例** 历史数据迁移用于将旧表中已有的消费记录搬迁到分库分表后的新表；业务双写负责同步启用后的增量变更。

2. 描述流程启动时，应说明触发启动的事件，以及启动前必须满足的条件。

   **示例** 用户提交历史迁移批次的启动请求，是触发启动的事件；批次处于“未启动”或“已暂停”状态，是允许启动的必要条件。收到请求后，后端仍需检查批次状态，不能直接启动迁移。

3. 描述流程中步骤之间的衔接时，应说明执行下一步所需的前一步结果、外部事件或其他条件。

   **示例** 历史迁移批次的状态更新和任务清单初始化事务提交成功后，才调度迁移任务；事务未提交成功时，不应开始调度。

4. 编写或压缩流程说明时，如果相邻动作由不同的人或程序执行，或一个动作每次请求都执行、另一个只在特定时机执行，应分句写清谁在什么时候做什么。

5. 后一步依赖某个条件时，将条件写在该步骤前。编写功能总述时，如果后一步依赖前一步留下的消息、任务或状态，讲清谁留下了什么、后一步由谁在什么时候使用它，以及这样解决了什么问题。

   **示例** 迁移期间，业务在旧表新增、修改或删除一笔流水时，会在同一个旧库事务里向本地消息表写入一条同步任务。事务提交后，后台读取任务，把这次变更同步到新表。所有旧表写入口都启用这套机制后，迁移批次才首次固定历史扫描范围。这样，已经搬过的流水再次被修改，也有后台任务负责同步。

6. 编写功能总述时，保留理解主问题答案所必需的内容。只用于回答某道已确认独立追问的内容，放到该追问的答题文档中。

7. 流程涉及状态变化时，应说明变化前后的状态，以及状态变化对后续处理的影响。

   **示例** 历史迁移批次从“运行中”变为“暂停中”，表示系统开始停止后续处理并等待正在执行的操作收尾；此时不能直接认定批次已经安全暂停。

8. 描述流程结束时，应说明判定结束的条件，并区分正常完成、暂停和异常终止等实际存在的结束情况。

   **示例** 历史迁移任务全部成功，批次才能判为“已完成”；迁移尚未完成但执行中的操作已安全收尾，才可判为“已暂停”。存在任务失败或结果不明时，应标为“异常待处理”，不能当作迁移完成。

9. 描述流程中的步骤时，应说明为什么需要执行该步骤。

   **示例** 历史数据迁移完成后，应比较新旧表的数据是否一致，因为迁移任务执行成功只能说明任务已完成，不能证明两端数据一致。

10. 描述流程时，应保留理解过程所必需的中间步骤，不能省略后让读者自行推断。

   **示例** 说明消费记录写入新表的过程时，不能从“计算分片编号”直接跳到“写入数据库”，还应交代根据分片编号确定目标 MySQL 实例和物理表这一步。

### 1.1.6 避免重复说明

1. 多处内容需要说明同一事项时，可以集中说明，避免重复；集中说明时，应明确适用范围，保留各处不同的条件或要求。

   **示例** 已经说明消费记录按商户号计算分片，并据此确定目标库表后，后续描述向该表写入记录时，无需再次展开相同的分片计算规则。

   **示例** 假设业务双写和历史迁移的方案都已确认，但均未实现，可以统一说明：“以下业务双写和历史迁移均为已确认方案，尚未实现。”不必在介绍两部分时分别重复。

### 1.1.7 因果表达

1. 使用“因为”“所以”等因果表述时，应确认所述因果关系有依据，不能自行推断并写成确定结论。

2. 将某个结果归因于某项做法时，应确认该做法是否足以产生这一结果；如果还需要其他机制或条件，应在对应内容旁说明。

   **示例** 不能说“启用业务双写后，新表就拥有全部消费记录”。双写只同步启用后的增量变更，新表要具备完整数据，还需要迁移已有的历史记录。

3. 多个结果分别依赖不同机制时，应说明每个结果由什么机制产生，不能把所有结果都归因于同一项做法。

   **示例** 不能把“历史记录进入新表”和“后续业务变更同步到新表”都归因于业务双写。历史记录由历史迁移搬入，双写负责同步启用后的增量变更。

4. 使用“因此”“所以”等词引出结论时，前文应已说明支持该结论的必要理由，不能只交代背景或判断条件就直接推出结论。理由尚未展开时，可以先直接提出核心结论，再解释理由，但不要使用表示前文已完成论证的连接词。

   **示例** 只说明“批次为未启动时才初始化任务”，还不足以直接接“因此，任务初始化和状态更新必须在同一事务中”。应先说明分别提交可能留下“任务已保存、批次仍未启动”的结果，以及后续请求会再次进入初始化分支，再引出同一事务的作用。

### 1.1.8 选择依据

1. 涉及方案或做法的选择时，应说明选择标准，以及所选方案或做法为什么符合这些标准。

   **示例** 消费记录的大多数查询场景都以商户为维度，比如异常回查，因此选择商户号 `merchantNo` 作为分片键，使按商户查询时能够根据分片规则定位对应分片。

### 1.1.9 方案影响

1. 说明所选方案或做法时，应交代采用后带来的主要收益和代价。

   **示例** 按商户号分片，有利于将带商户号的查询定位到对应分片；但缺少商户号及其他分片定位信息的查询，可能需要访问多个分片并合并结果。

### 1.1.10 风险说明

1. 说明风险时，应交代判断依据、触发条件及具体后果。后果依赖后续流程的判断或操作时，应说明异常发生后留下了什么结果，后续流程依据什么规则处理，以及最终造成什么影响，不能省略中间环节或只写“存在风险”“状态不一致”等概括性结论。

   **示例** 如果先将批次状态改为“运行中”并提交，随后任务初始化失败，数据库就会留下“批次运行中、任务清单不完整”的结果。后续启动请求读取到“运行中”后会拒绝启动，因此无法通过正常启动流程补齐任务。

2. 说明异常处理或防御性检查时，按以下步骤核对。

   - **先核对这个场景在项目中能否发生。** 拟题、写答案或复核旧稿时，先说明发生这种情况需要什么条件，再用已确认的业务规则、数据情况和现有保障逐项核对。旧稿或汇总中提过的场景，也要核对它是否适用于本题。

   - **再判断这个场景是否影响答案。** 有依据说明该场景可能发生，而且它会改变本题的判断或处理方式时，才写入考点或口述。已确认的事实足以排除该场景时，从本题中去掉。材料不足时，只有补齐信息会影响答案，才列为待确认事项，并写清需要确认什么。

     **示例** 本次迁移的旧表已有五个自然年的流水，因此可以排除“首次启动时整张旧表为空”。“某个任务读不到流水”则需要另一个条件：该任务覆盖的整个主键区间里一条记录都没有。主键从 `100` 跳到 `103`，只能说明中间缺了两个编号。项目材料没有显示存在整段空缺时，口述写清“每个任务按主键分页，搬运自己区间内实际存在的流水”就够了。

   - **异常属于哪种方案** 当前方案已经排除的异常，可以用来解释方案取舍。举例时，写清采用哪种做法才可能出现这个异常。

   - **项目怎样处理异常** 将检查、告警或人工处理写入项目流程前，核对材料是否同时说明了触发条件和处理动作。依据不足且影响结论时，将缺少依据的内容标为「待确认」。

   **示例** 任务初始化和批次状态更新在同一事务中完成，中途失败并完整回滚后，本次写入的任务也会撤销。“任务已保存、批次仍未启动”可以用来解释分别提交的风险。若关联方案只写了“发现已有任务时拒绝继续初始化”，就按该条件描述拒绝动作。要写“交由人工核实”，还需核对恢复规则是否明确适用于这个分支。

### 1.1.11 结论的确定程度

1. 改写结论时，应保留原有确定程度，不能把“可能发生”改成“必然发生”。

### 1.1.12 对比组织

1. 对比内容按主题划分，每个对比项只围绕一个主题展开。

2. 每个对比主题下，先说明各对象与该主题有关的相同点，再分别说明不同点；没有相同点时，应明确说明该主题下没有相同点。

3. 同一对比主题下，分别介绍各对象时，每个对象单独成段。

4. 分别介绍对比对象的段落，以 `**对象名称：**` 开头，填写实际对象名称。

5. 对比内容的各段之间空一行。

### 1.1.13 示例使用

1. 说明方案解决的问题或核心机制时，如果仅靠概括难以理解，应补充示例。

2. 示例只围绕当前要解释的内容展开，并交代理解该内容所需的信息。

3. 已有解释足够清楚时，不强制添加示例。

4. 材料中已有的示例经核实正确，且适合解释当前内容时，应优先使用。

5. 新增教学示例时，应明确标注为示例。

## 1.2 数值参数说明

1. 涉及数值参数时，应说明参数的含义、作用对象和适用条件；需要单位才能准确理解数值时，应注明单位，数量类参数不必机械补充“个线程”等单位表述。

   **示例** `ThreadPoolExecutor` 的最大线程数 `maximumPoolSize`，表示该线程池允许存在的最大工作线程数量。线程池处于运行状态时，如果任务无法进入队列，且当前线程数未达到该上限，线程池会尝试创建新线程处理任务。

2. 写出参数的具体取值或范围时，说明为什么选择这个值或范围。取值已经确认、理由尚未核实时，保留已确认的取值，并注明「取值依据待确认」。

3. 应标明参数值是项目确认值、参考值、示例值还是建议压测值，不将建议或示例写成实际配置。

4. 数值参数有可靠依据时，应给出具体数值或范围，不用“适量”“短暂”“合理配置”等模糊表述代替。

5. 项目实际取值尚未核实时，注明「实际取值待确认」，不编造数值。

## 1.3 项目事实与验证情况

### 1.3.1 区分实际内容与示例

1. 正文应区分项目实际使用的内容与示例，不能将示例写成实际实现。

### 1.3.2 区分方案、实现和验证状态

1. 正文涉及项目方案时，不能将设计已确认说成功能已实现，也不能将功能已实现说成效果已验证。

2. 正文中的结论涉及尚未实现的功能或尚未验证的效果时，若这会影响结论成立，应说明具体缺少什么实现或验证，以及对结论的影响，不能只标注“待验证”。

### 1.3.3 说明验证情况

1. 文档涉及验证结果时，应说明实际检查了什么，以及采用了什么检查方式。

2. 说明验证结果时，应明确结果能够支持哪些结论，以及不能据此得出哪些结论。

3. 只有实际执行了相应检查或测试，且结果支持对应结论时，才能将该结论标为“已验证”。

4. 文档中仍有项目事实需要确认，或仍有结论需要通过检查、测试来验证时，按[标注状态](/C:/Users/Administrator/.codex/skills/java-interview-doc-workflow/references/interview-document-writing.md:191)中的规则分别标明。
