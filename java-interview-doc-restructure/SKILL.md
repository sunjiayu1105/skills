# 1 明确范围和用户要求

读取目标文档、项目规则及直接相关的主分文档和引用，了解已确认结论、内容归属与待验证事项。目标不明确时先确认。

用户明确提出拆分或重组要求时，按用户要求执行；未提出时，依据本技能的判断原则，自行确定是否需要拆分或重组，以及具体方案。

执行拆分前，按第 2.1 节分析原文并筛选高级 Java 面试核心考点。在对话中展示筛选结果和完整拆分方案。

1. 说明相似面试题实际问到了候选题的哪些内容。
2. 结合原文场景，说明候选人需要作出什么重要判断，以及为什么值得作为高级 Java 核心考点独立成篇。

   **示例** 公开题问「线程池的线程数应该怎么配置？」这是第一条的依据。历史迁移场景要求候选人判断增加线程会提高吞吐，还是加剧数据库连接等待。这项容量取舍是第二条的依据。[《面渣逆袭·Java 并发》第 61 题](https://javabetter.cn/sidebar/sanfene/javathread.html)

在拆分方案中，逐题列出准备独立成篇的追问，注明它承接哪道题、题目来源，以及为什么值得单独讲。

**示例** 「为什么历史迁移选择 `AbortPolicy`？」承接「线程池容量与调优」，来源标为「基于项目拟题」。独立成篇的理由是，这道题考察拒绝策略如何影响任务派发和数据库并发。

说明每篇文档回答的问题、内容归属、主分关系、文件名与编号，以及受影响的引用。用户确认方案后，再执行拆分。

技术核验、事实边界、考点覆盖和口述表达遵循 [java-interview-doc-workflow](../java-interview-doc-workflow/SKILL.md)。整理后的连续复核按第 5 节执行；依赖缺失时说明缺失项，不宣称相关步骤已完成。

# 2 判断如何拆分或重组

## 2.1 分析并筛选高级 Java 面试核心考点

### 2.1.1 从原文提取候选题

1. 通读原文和直接相关文档，结合实际内容找出值得追问的问题。

2. 将每个候选题写成一个明确的问题，并标明它来自原文哪一节。

   - **原文位置** 《断点续跑》的「写入成功但进度保存失败」小节。
   - **候选题** 目标库已写入，但迁移进度保存失败。服务重启后应从哪个位置继续迁移？

3. 用一两句话直接回答候选题。

4. 写清本题需要讲到哪里。适合由其他题展开的内容，标明对应主题。

   - **简要答案** 从最后一次确认已持久化的进度继续，重放进度未确认的那一页。该页可能已经写入，因此重放必须满足幂等要求。
   - **答题范围** 本题讲如何确定恢复位置，以及为什么重放需要幂等。唯一约束和版本比较的具体做法由「重复写入幂等」一题展开。

5. 提取候选题时，以范围内原文的完整技术内容为起点。按正文逐节找出需要候选人独立解释、判断或取舍的内容，并标明它由哪道现有题覆盖、是否需要新增候选题，或为什么只需留在流程说明中。多个内容归入同一道题时，核对该题的问法和答案是否实际覆盖各项判断。完成这一步后，再核对公开题依据并决定是否拆分。

6. 对拟归入已有题目或仅保留在流程说明中的内容，复核其中是否包含值得独立考察的技术判断。若有，写出候选题，并核对已有题的问法和答案能否直接回答。已有题尚未覆盖的，纳入候选清单，再按后续规则判断是否独立成篇。

### 2.1.2 核对相似面试题

为每个候选题查找可公开追溯的相似面试题，记录原题、链接和来源类型。

1. **题目覆盖范围。** 说明公开题问到了候选题的哪一部分。业务场景不同时，写清两题共同考察的内容。

2. **核对范围。** 只看到搜索摘要时，注明「仅核对搜索摘要，原帖正文待核对」。

3. **是否实际问过。** 引用个人面经时，写「据发帖者自述，面试中被问到这道题」。引用招聘方样题时，写「这是公开样题」。引用第三方题库时，写「这道题被题库收录」。

4. **岗位级别。** 来源明确写明岗位级别时，按原文记录。来源只写「Java 后端面试」时，标注「岗位级别未说明」。

5. **出题频率。** 来源交代了样本范围和出现次数，才能描述该样本中的出题频率。只找到一篇面经时，写「找到一条面经记录」。

**示例** 公开题库收录了「线程池怎么关闭知道吗？」，覆盖线程池关闭。「历史迁移中如何确认在途数据库操作已经结束？」标为「基于项目拟题」。该题库条目未说明岗位级别，也未提供出题频率统计。[《面渣逆袭·Java 并发》第 60 题](https://javabetter.cn/sidebar/sanfene/javathread.html)

### 2.1.3 判断高级 Java 核心性

1. 说明候选人需要解释什么机制、作出什么判断，或权衡哪些方案。

2. 给出一个具体场景，说明判断错误会带来什么后果。

3. 相似题只覆盖定义或基础用法时，单独说明候选题的进阶考察价值。

### 2.1.4 决定是否拆分

1. 候选题与原文直接相关、具有独立回答价值，且面试相关性和核心性都有充分依据时，才纳入核心考点拆分方案。

2. 面试追问能形成一个明确问题、能从原文找到依据，并且能考察上一级问题尚未覆盖的技术判断时，独立成篇。用于解释上一级结论的简短说明，留在上一级文档。

   **示例** 「线程池容量与调优」讲线程数、队列容量与数据库连接预算。「为什么历史迁移选择 `AbortPolicy`？」可以独立成篇。原方案采用 `AbortPolicy`，任务被拒绝时由提交方停止派发，再核对已接收和未提交的任务。追问考察提交线程能否兼做迁移工作。线程池饱和且仍在运行时，`CallerRunsPolicy` 可能让提交线程在已有工作线程之外再执行写库任务，影响数据库并发和派发流程。

3. 追问独立成篇后，上一级文档保留回答本题所需的简短结论，并链接到追问文档。

   **示例** 「线程池容量与调优」保留一句「任务被拒绝时，提交方停止派发，并核对已接收的任务」，再链接到「为什么历史迁移选择 `AbortPolicy`？」。两种拒绝策略对提交线程和数据库并发的影响，在追问文档中展开。

4. 每篇追问只归属一个直接主文档。根据追问具体承接哪个问题确定归属。一篇追问也可以作为下一层追问的主文档。

   **示例** 「为什么历史迁移选择 `AbortPolicy`？」承接「线程池容量与调优」中的队列和派发设计，因此归到「线程池容量与调优」下面。

5. 有公开面试题依据的，注明原题、出处和实际覆盖范围。根据项目内容自行判断并拟出的问题，标为「基于项目拟题」，并说明为什么值得问。

   **示例** 「线程池的拒绝策略有哪些？」有公开题库出处。「为什么本项目选择 `AbortPolicy`？」标为「基于项目拟题」。它承接上一题，具体考察候选人能否说明拒绝策略对任务派发和数据库并发的影响。[《面渣逆袭·Java 并发》第 57 题](https://javabetter.cn/sidebar/sanfene/javathread.html)

6. 每个入选考点独立成篇，按考察内容确定文档边界。每篇追问回答一个问题，同题优先复用已有文档。

### 2.1.5 检查口述长度

拆分后，每篇文档的面试口述尽量控制在 300 字符以内，按 `java-interview-doc-workflow` 的口述字符数规则统计。超过 300 字符时，先判断能否拆出可独立回答的追问。如果再拆会影响回答的完整性，可以超过 300 字符，并在拆分方案中说明原因。保留理解回答所必需的前提、理由和技术边界。

按考点拆分，每题一篇，不按长度平均切段。支持多级拆分，分文档仍然过长时，沿用同一条件判断是否继续拆分，不限制层级或篇数。

## 2.2 确定内容归属

比较各篇的问题、处理对象、触发条件、机制和结果，决定保留、合并、拆分或调整归属。同一问题优先复用并更新已有文档，不能因标题、措辞或示例不同就另建一篇。

必要的共同前提和简短结论可以重复；详细内容只设一个主要维护位置。若一篇文档只剩其他文档的摘要或交接说明，没有独立问题，应并入对应文档。

依据内容建立覆盖范围内全部文档的主分关系清单，逐篇记录：当前文件名、核心问题、直接主文档、归属依据、目标文件名和目标编号。没有直接主文档的，注明是整组主文档还是独立文档；每篇分文档只归属一个直接主文档，同时可以作为下一级文档的主文档。

不能仅凭现有文件名前缀判断归属，也不能把相互引用直接当作主分关系。按第 4 节生成清单中的目标文件名和编号；后续拆分、合并或调整归属时同步更新清单，以此作为修改和复核的依据。

# 3 整理主文档和分文档

## 3.1 主文档回答总体问题

保留指定文档作为主文档，讲清目标、必要前提、主要流程、关键做法、阶段衔接和完成条件。涉及追问时，概括谁在什么条件下做什么、解决什么问题，不能只列目录或链接。

将符合第 2.1 节条件的深入内容移入分文档，如参数推导、配置、代码、详细示例或异常处理。理解总体答案必需的解释仍留在主文档。

## 3.2 分文档回答具体问题

每篇只回答一个明确问题，按“直接结论 → 必要依据或过程 → 限制与待验证边界”组织。流程按执行顺序讲述，并列机制分别说明；使用简短标题和易懂表述，把条件、原因和结果放在对应动作旁。

每一层都保留回答自身问题所需的背景、做法、理由和关键步骤，使读者不必先看其他文档也能理解。其他主题只保留必要交接和链接，不能为缩短篇幅而破坏回答的完整性。

## 3.3 完整迁移内容

拆分或合并时，将对应的口述、详细解释、示例、来源、已确认规则和待确认、待验证事项一起迁移，保留技术前提、失败边界及来源对应关系。共同约束在主文档统一说明，分文档保留理解答案必需的部分并引用来源。

迁移后，原位置保留必要概括和链接，删除重复展开。核对独有内容均有去向后，才删除已无独立问题且获准删除的原文件，并同步引用。

# 4 统一命名、编号和引用

## 4.1 命名

分文档使用 `三位编号_总文档主题_追问主旨.md`。总文档主题是其文件名去掉开头编号及下划线、末尾 `.md` 后的完整名称；追问主旨应简短、准确。一级标题与文件名一致，不包含 `.md`。

例如：

- 主文档：`012_不停机数据迁移_在线历史迁移_批次处理逻辑.md`
- 分文档：`013_不停机数据迁移_在线历史迁移_批次处理逻辑_启动互斥.md`

依据主分关系清单，从主文档到下级文档依次生成目标文件名。多级拆分时，总文档主题取直接主文档的目标文件名中的完整主题，再追加本篇追问主旨，不重复拼接数字编号。

对范围内全部文档执行命名核对，包括没有新增拆分、没有正文修改或此前已改过名的文档，不能因此跳过。用户明确指定的命名要求优先；若与本次要求的主分命名规则冲突，应列出具体文件和冲突点请用户明确取舍，不能默默豁免后宣称全部符合规则。

## 4.2 连续编号

先按内容的理解依赖和实际执行顺序排列文档，再分配编号。读者需要先理解哪篇，哪篇就排在前面。例如，三篇分别讲理由、结论和实现方案时，按“理由 → 结论 → 实现方案”排列。

主分文档默认相邻排列。若主分顺序与内容依赖冲突，在拆分方案中列出冲突和拟采用的顺序，待用户确认后按确认顺序编号。

将已有和新增文档一起排列，使用连续三位编号，不使用子编号。默认按“主文档 → 其分文档及下级 → 下一个同级文档”排列。用户已指定顺序和起始编号时，按其要求执行。

编号冲突时，将原占用文档及后续受影响文档按原顺序顺延，保持编号连续且不重复。`999` 编号文档不参与顺延，不覆盖或删除其内容。只处理必要的冲突；超出授权范围时，先列出影响再确认。

## 4.3 同步引用

同步受影响的文件名、一级标题、主分导航、摘要、术语和关联引用，检查链接目标及移动后的行号，避免失效链接和无归属的来源或待验证事项。

# 5 连续复核与交付

1. 拆分完成后，使用 [java-interview-doc-review-loop](../java-interview-doc-review-loop/SKILL.md) 对主文档、新增或修改的分文档，以及必要的关联修改进行连续复核。

2. 每轮按 [java-interview-doc-workflow](../java-interview-doc-workflow/SKILL.md) 核验技术结论及答案来源，整理面试口述和详细方案。

   **示例** 拆出「并行任务断点续跑」后，由 review 核对「从最后一次确认已持久化的进度继续」成立的条件，再把恢复位置和安全重放的前提整理进面试口述与详细方案。

复核中再次拆分的文档也纳入范围；停止条件和复核记录遵循连续复核技能。

复核既检查单篇表达和考点覆盖，也检查整组文档的迁移完整性与结论一致性。若口述重新堆积过多内容，回到第 2 节判断。

逐篇统计并报告面试口述的字符数，说明超过 300 字符的原因。按用户确认的顺序核对编号是否连续、内容依赖是否得到满足。

以最新主分关系清单为准，逐篇核对以下完成条件：

- 逐篇核对候选题对应的原文、相似面试题的原题及出处，以及高级 Java 核心性判断。
- 确认题目出处支持所声明的考察范围，自行拟出的问题已标为「基于项目拟题」。
- 逐篇核对追问是否承接直接上一级的问题、能否独立回答，以及上一级是否保留了必要结论和追问链接。

  **示例** 复核「为什么历史迁移选择 `AbortPolicy`？」时，检查该篇能否独立讲清选型理由，并确认上一级「线程池容量与调优」仍说明任务被拒绝后如何处理，且链接指向这篇追问。

- 发现入选依据不足时，按第 2.1 节重新判断内容归属，并同步修正拆分方案。
- 正文内容支持清单中的归属，每篇分文档只有一个直接主文档。
- 实际文件名与目标文件名一致，分文档继承直接主文档的完整主题。
- 实际编号与拆分方案中经用户确认的顺序及目标编号一致，且连续排列。
- 实际文件名、一级标题、主分导航和关联引用同步一致。

发现偏差时，在授权范围内修正后重新核对；无法处理的，列出具体文档、偏差和阻塞原因，不得宣称整组复核通过。一级标题与文件名一致、链接有效，都不能单独证明主分命名符合要求。

交付时展示最终主分层级，说明拆分与合并依据、实际新增修改删除的文件及重命名对应关系，并报告静态检查结果和未解决事项。
