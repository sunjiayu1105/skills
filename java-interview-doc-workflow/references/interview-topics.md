# 1 筛选与确认面试考点

“问题”是面试官会问的话。“考点”是希望候选人通过回答讲清的内容。一个问题可以考查多个要点。

先确定本次使用哪份考点清单。沿用已有考点时，从导航中读取已确认的问题和答题范围。重新选题时，依次挖掘考点、拟定问题，并逐个写入《候选问题清单》。用户确认后，将入选问题归档到导航。

## 1.1 确定沿用已有考点还是重新选题

### 1.1.1 沿用已确认的考点

1. 用户决定沿用考点时，到《面试考点_导航》的「已确认考点」章节查找。找不到这份清单，再请用户指定。

## 1.2 挖掘候选考点

1. 挖掘考点时，对照《面试考点_已确认规则》，将用户指定要考查的考点全部纳入候选清单，移除用户明确排除的考点。继续从本轮材料中挖掘其他值得考查的内容，符合要求的一并列入清单。

### 1.2.1 判断材料能否引出候选考点

1. 如果根据材料中的业务目标、约束或已知现象，能说清希望候选人解释什么，就可以将其列为候选考点，即使材料还没有说明具体做法。

### 1.2.2 从公开面试题发现考查角度，再回查项目

1. 先找搜索词。 看项目用了什么技术、要解决什么业务问题。用技术名查一次公开面经和题库，再用业务问题的问法查。

   **示例** 多个实例可能同时启动同一批次时，既可以查“分布式锁面试题”，也可以查“如何防止任务重复启动”。

2. 看原题问了什么。 写清候选人需要解释什么。原文列有追问时，再看追问多问了什么。即使原文没有注明岗位级别，也可以从问法中找考点。

   **示例** “怎样给同一批次加锁”考查锁的使用方式。“持锁期间锁过期会怎样”考查锁失效对后续操作的影响。

3. 看这个问题是否适用于项目。 先查项目中有没有原题描述的情况，再看它能用来考查项目中的哪项做法或选择。有材料支持，就列为候选考点。缺少会影响判断的信息，就写明还需要确认什么。

   **示例** 原题问“持锁期间锁过期会怎样”。先找出批次启动时哪些操作需要持锁，再查锁有没有可能在操作完成前到期。如果可能，就看接下来的哪一步会受影响。

### 1.2.3 从项目材料和用户关注的问题中提取考点

逐个查看项目功能，先弄清它要解决什么问题、有哪些已知约束，再从下面适用的角度提取考点。材料已经说明具体做法时，结合该做法继续挖掘。项目材料本身足以说明为什么值得考查时，即使没有找到公开相似题，也可以列为候选考点。

1. 用户想了解什么。 把用户明确提出的场景都纳入考查范围。

   **示例** 用户想了解迁移批次怎样启动，就要涵盖首次启动和暂停后再次启动，讲清两种情况下各自的完整流程。

2. 整体方案。 找出共同解决一个业务问题的几项设计，考查它们怎样配合。

   **示例** 不停机迁移时，已有流水怎样搬到新表？迁移期间发生的变更又怎样同步过去？

3. 功能流程。 跟着一次请求或一笔数据变更往下看。每一步由谁执行？什么时候执行？得到什么结果？下一步怎么用这个结果？如果条件不同会走不同的流程，就分别梳理。

4. 技术选型。 逐节查看《整理初稿》，找出项目选用的技术、组件和实现方案。对每项选择，查清项目为什么需要它、为什么选这个方案、做过哪些有依据的取舍。已有问题讲过的，记下对应问题。值得问但还没讲到的，列为候选考点。材料没交代选择理由时，写明缺哪项依据。

   **示例** 《整理初稿》同时涉及「为什么引入消息队列」和「为什么选择当前消息队列产品」时，将两项选型分别核对。

   **示例** “同一批次怎样加锁和释放锁”问的是用法。要判断“为什么选择 Redisson 的 `RLock`”是否值得问，还要查项目对锁键、租约以及释放锁前检查持有者有哪些要求。材料能说明这些要求怎样影响选择，就把选择理由列为考点。

5. 机制能解决什么问题。 对照已有问题，看它们是否讲清机制保护哪些操作、关键参数怎样影响结果，以及机制失效后会发生什么。把遗漏且值得问的内容列为候选考点。需要先核实项目事实才能判断时，写清要核实哪件事。

   **示例** “启动锁在事务提交前到期，哪个实例有资格派发任务？”问的是锁过期后的处理。如果清单里只有这个问题，还要看看是否需要考查锁本身的设计，包括哪些请求竞争同一把锁、什么时候加锁、保护哪些操作、什么时候释放。

   **示例** 假设启动锁保护批次状态的读取和更新、任务初始化以及恢复条件检查，就把这些操作列清楚。若任务提交和派发是在事务提交、锁释放之后执行，还要说明这两步由后续流程负责。

   **示例** 如果锁的租约固定为 15 分钟，就核对处理批次状态的事务最长要执行多久。若事务还没提交锁就可能到期，再查清这会影响哪一步。

6. 什么时候可以进入下一阶段。 找出开始下一阶段前必须满足的条件，再问怎样确认这些条件已经满足。

   **示例** “把业务写入切换到新表之前，怎样确认新旧表的数据一致性校验已经通过？”

7. 故障后怎样恢复。 从项目中可能出现的一次故障入手，查清中断前哪些操作已经完成、系统根据什么决定从哪里继续，以及怎样确认恢复成功。

8. 从项目材料中提取考点时，也可以考虑数值参数的取值。选多大需要权衡、调大或调小会影响系统行为时，可以把“怎样选择这个值”列为候选考点。只用于举例或交代背景的数值，随相关内容说明即可。

   **示例** 历史迁移的任务区间划得越小，需要创建和派发的任务就越多，但不同线程也更容易分摊剩余工作。因此，可以考查“怎样选择单个任务的主键区间跨度”。

9. 架构设计

   1. 围绕一项业务目标，把不同文档中描述同一方案的内容放在一起看。沿着一次请求或一次数据变更，梳理各模块分别负责什么，以及一个模块的处理结果怎样交给下一个模块。

   2. 从业务约束中提取候选考点。例如，哪些操作必须一起成功？哪些步骤可以异步完成？一个模块变慢或失败后，其他模块怎样继续处理？

   3. 材料缺少具体做法时，结合已知项目条件和可靠资料补充可行方案，说明它怎样解决问题，并标为「建议方案」。如果某项未知条件会改变设计选择，写清需要核实什么，以及它会怎样影响方案。项目实际采用的做法经核实后再写入。

   4. 拟定问题时，先看已有问题的答题范围。讲清整体方案就能覆盖的考点，归入主问题。候选人介绍做法后，如果还有值得单独解释的设计理由、取舍或故障处理过程，再据此拟定追问。

   **示例** 材料说明“历史数据迁移期间，业务仍会修改旧记录”，就可以问：“迁移期间，怎样避免旧值覆盖用户刚修改的新值？”如果材料没有交代写入机制，可以补充一项建议：当同一记录的两次变更有可比较的版本，且目标表能在一次写入中完成版本判断和更新时，只允许较新的版本覆盖现值。这里需要核实的是**版本从哪里来，以及两条写入链路是否遵守同一套比较规则**。

### 1.2.4 从已有回答中挖掘追问

1. 从候选人已经讲到的业务场景、系统能力、处理结果或具体做法中，找出值得进一步解释的内容。回答只讲了系统能做什么时，可以追问怎样做到；回答已经讲了做法时，可以追问选择理由、适用条件或异常情况。

   **示例** 候选人说“历史迁移可以暂停，之后还能继续搬数据”。可以先问：“暂停后再次启动，系统怎样确定从哪里继续搬？”如果候选人回答“每页写完后保存进度”，再问：“如果这一页已经写完，进度却没保存成功，下次启动会怎样处理？”

2. 写清回答这个追问还需要讲明白什么，再用前两节的方法判断这一点是否值得考查。可以沿用已经核实的公开相似题，也可以结合项目材料或用户明确关心的问题判断。值得考查的，把追问要考查的内容列为候选考点。

## 1.3 根据考点拟定问题

### 1.3.1 组织考点并写出问题

1. 整理考点。先用一句话写清每个考点希望候选人讲明白什么。如果多个来源考查的是同一件事，就合并为一个考点，保留各自的依据。

2. 把考点写成问题。几个考点合起来才能讲清一个流程或解释一个选择时，围绕这个流程或选择提一个问题，让问法涵盖每个考点。几个考点各自可以讲清时，可以分别提问。

   几项改造各自的原因可以独立讲清时，分开问。需要结合几项改造才能解释共同原因时，合在一起问。

   涉及多个组件时，顺着一次请求或一笔数据变更，梳理每一步由谁处理、得到什么结果，以及下一步怎样使用这个结果。需要联系几个环节才能解释的问题，放在一起问。

   **示例** 梳理 MySQL 到 Canal 的采集流程时，“首次上线时怎样确定两个 MySQL 实例各自的采集起点”和“Canal 怎样把日志中的多行变更组织成消息”可以分开问。要解释“Canal 重启后为什么可能重复投递”，则要在同一回答里讲清消息是否已送达 RocketMQ，以及 Canal 是否已保存对应的采集进度。

3. 合并重复问题。比较候选问题各自要求讲清什么。如果答完一个问题也就答清了另一个，就合并，保留两者涉及的考点。已有问题只需补充一句解释就能讲清的术语或步骤，归入它的答题范围。

4. 插入必要问题。如果当前问题用到了候选人还没介绍的业务背景或项目做法，就在它前面补一个问题，请候选人讲清相关情况，再根据回答提出原本要问的问题。

   **示例** 想考查迁移批次首次启动的流程，以及暂停后再次启动的流程。可以先问“你们怎样迁移旧表中已有的流水？”等候选人讲到按批次迁移，并介绍了批次可以暂停和恢复，再把两个考点合在一起问：“批次首次启动时，系统怎样处理？暂停后再次启动时，又怎样处理？”

5. 问题中提到项目采用了某项具体做法时，先核实这个前提。材料只说明了业务场景时，从已知场景出发，问候选人会怎样处理。需要讨论某个备选方案时，在问题中写明假设条件。

   **示例** 材料只写了“多个实例可能同时启动同一个迁移批次”，面试官可以先问：“两个实例同时请求启动同一个批次，你会怎样避免它被启动两次？”

   如果候选人回答“我们按批次 ID 加分布式锁”，就可以顺着问：“拿到锁之后，你们在哪一步判断这个批次还能不能启动？”

   如果候选人还没提到锁，面试官也可以把它作为假设提出：“假设两个请求按同一个批次 ID 加锁，第一个请求释放锁后，第二个也拿到了锁。你会怎样判断第二个请求还能不能启动这个批次？”

### 1.3.2 确定主问题，再把追问接到对应的回答后面

1. 直接想了解什么，就围绕它设主问题。主问题可以问整体方案，也可以独立问一个功能的完整流程、一项机制怎样解决问题、为什么选择某个方案，或故障后怎样恢复。

2. 几项设计共同解决一个业务问题时，检查现有问题能否让候选人讲清为什么需要整套方案、有哪些关键设计、它们怎样配合。如果已有问题只问了局部做法，就补一个整体方案主问题。

   **示例** 已有“为什么选商户号作为分片键”和“一笔流水怎样定位到具体库表”两个问题时，可以先问“为什么要对消费记录做分库分表？整套方案是怎样设计的？”等候选人介绍分片键和路由方式后，再分别追问选商户号的理由和具体的路由计算。

3. 安排追问时，写清它接在哪个问题后面。前一个回答已经介绍的做法，就是追问的起点。

   **示例** 直接讨论迁移批次启动时，“首次启动和暂停后再次启动时分别怎样处理”可以作为主问题。如果先讨论不停机迁移，等候选人介绍了按批次搬运流水以及批次可以暂停和恢复，同一个启动问题就可以作为追问。

### 1.3.3 写清每个问题的考点

1. 在每个主问题和追问下分别列出本题的考点。一个考点只阐述一个可以单独讲清的要点。一个问题涉及多个考点时，逐项列出。

2. 每个考点写清希望候选人解释什么，让读者看得出回答时需要讲明白哪件事。

   **示例** 对于「历史迁移批次首次启动和暂停后再次启动时，系统分别怎样处理？」，可以列出两个考点：

   - 首次启动时，系统怎样确定扫描范围、创建任务清单，并判断何时可以派发任务。
   - 暂停后再次启动时，系统怎样确认上次执行已经收尾，并根据原任务清单和已保存的进度继续迁移。

### 1.3.4 写清每个问题要答到什么程度

1. 整体方案。 先用一句话写清总述要回答什么。问题过宽时，先收窄问法。逐项判断省去某项设计后，听者还能不能理解方案怎样解决问题。理解方案所必需的设计放进总述，必须配合才能讲清的几项设计放在同一个考点下。

   **示例** 分库分表总述要讲清为什么拆、库表怎样划分，以及一笔流水怎样找到对应库表。实例数和表数影响理解时，再交代具体数量。商户号的选取理由和具体路由计算可以在对应追问中展开。

2. 整体改造计划。 对照完整的《整理初稿》，检查计划是否覆盖本次改造涉及的全部功能，并补上遗漏的功能。每项功能都要交代在哪个阶段实施、开始前需要满足什么条件、怎样确认这个阶段已经完成。

3. 独立功能和技术问题。 问完整流程时，把问题点名的每种场景都列入答题范围。问机制、选型或恢复时，把会改变技术选择或处理步骤的项目条件列入答题范围。

4. 追问。 写清原问题已经回答了什么，以及追问还需要解释什么。只在追问时才用得上的内容，放在对应追问文档中。新增追问后，仅在主问题的答案也需要补充时调整总述考点。

### 1.3.5 核对候选问题的项目依据和公开相似题

#### 1.3.5.1 标明项目拟题依据

1. 根据项目材料自己拟出的面试问题，标为「基于项目拟题」。

#### 1.3.5.2 查找公开相似题，核对共同考点和项目特有要求

1. 先看前面查过的公开面试题。如果考点相同，就沿用已核实的原题、出处链接和来源类型，说明两者共同考查什么。遇到还没查过的考点，再围绕它补查。

2. 业务场景不同时，写清候选问题中哪些项目特有的做法超出了公开题的考查范围。

3. 如果公开题只问概念或基本用法，就写清项目问题还要求解释哪项做法、作出什么判断或权衡，以及为什么值得在高级 Java 面试中问。

#### 1.3.5.3 如实记录来源类型、岗位级别、核实程度和出题频率

1. 按来源记录。个人面经写「据发帖者自述，面试中被问到」，招聘方发布的问题样例写「公开样题」，第三方题库中的问题写「题库收录」。

2. 仅查到搜索摘要时，注明「仅核对搜索摘要，原帖正文待核对」。

3. 原文没写职级也可以收录，标注「岗位级别未说明」。写了职级就按原文记录。要写“某次高级 Java 岗面试问过这个问题”，需要找到能同时核实岗位级别和具体问题的面试记录，并注明来源类型。

4. 要说明一个问题出现得有多频繁，来源必须同时给出统计范围和出现次数，结论也只适用于这批样本。同一篇原文的多个转载只算一个来源。只查到一篇独立面经时，写「找到一条面经记录」。

### 1.3.6 将候选问题写入清单

1. 逐个判断拟好的问题是否与项目直接相关、能否独立作答、候选理由是否充分。用户明确关心的功能流程，值得单独讲清时也可以列入清单。

2. 每拟好一道问题，就把问题、考点和候选理由写入《候选问题清单》。

3. 需要说明这道问题要答哪些场景、讲到什么程度时，在「考点」和「候选理由」之间补上「答题范围」。

   - 问题 写出面试官会怎样问，用完整的问句表述。

   - 考点 写出希望候选人通过回答讲清哪些要点。一个问题可以有多个考点。

   - 答题范围（按需填写） 考点已讲清要答什么、讲到什么程度时，省略此项。需要限定适用场景、回答深度或与其他问题的分工时，只补充这些边界。如果是追问，注明它接在哪个问题后面、前面已经讲过什么、这次还要进一步解释什么。

   - 候选理由 说明为什么值得问。项目材料有依据，就注明位置和它能说明什么。找到公开相似题，就列出原题、出处链接和来源类型，写清共同考点。哪类依据没有，就省略哪一类。

     将出题频率作为候选理由时，按[如实记录来源类型、岗位级别、核实程度和出题频率](/C:/Users/Administrator/.codex/skills/java-interview-doc-workflow/references/interview-topics.md:170)中的规则，写明统计覆盖了哪些面试记录，以及该问题在其中出现了多少次。

4. 提交《候选问题清单》前，先对照本次项目材料，检查各项功能、技术选型和用户明确关注的问题是否都已考虑。再按本次适用的规则抽查依据或逐项核对结果。例如，候选理由中写了“高频”，就回查来源给出的样本范围和出现次数。发现遗漏时，先补齐，再提交。

## 1.4 归档已确认考点并更新文档

### 1.4.1 将入选问题写入面试考点导航

1. 用户确认后，将每个入选问题的完整条目写入导航文档的「已确认考点」章节，保留条目的内容和顺序。

### 1.4.2 按已确认考点安排答题文档，核对每个问题的链接

1. 如果需要拆分或重组文档，先按[面试文档拆分与重组](/C:/Users/Administrator/.codex/skills/java-interview-doc-workflow/references/document-restructure.md:1)提交方案，用户确认后再调整文档、整理答案。无需拆分或重组时，直接整理答案。

2. 答题文档确定后，逐个检查导航文档「已确认考点」里的链接，确保每个问题都指向回答它的文档。

### 1.4.3 补全汇总内容、更新引用后移除候选清单

1. 检查哪些内容目前只写在《候选问题清单》里。属于本次汇总范围的，先补进《整理初稿》。

   **示例** 如果入选问题涉及的项目事实还要核实，补进《整理初稿》时仍标为“待核实”。

2. 确定内容的新位置后，把原来指向《候选问题清单》的链接逐一改到对应位置。

3. 确认入选问题已完整迁入导航、每个问题都链接到对应的答题文档、《整理初稿》已补齐应保留的内容、原来指向清单的链接也已全部更新后，移除《候选问题清单》。

### 1.4.4 后续需要调整考点或答题范围时再次确认

1. 后续整理中，如果需要调整用户已确认的考点或答题范围，先说明想改哪里、会影响哪些内容。用户确认后，再更新相关文档。
