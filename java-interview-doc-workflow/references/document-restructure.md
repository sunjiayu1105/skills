# 1 面试文档拆分与重组

## 1.1 确定各篇文档写什么

### 1.1.1 《面试考点_已确认规则》记录什么

1. 《面试考点_已确认规则》记录用户明确指定要考查的考点、考查顺序，以及明确要求排除的考点

### 1.1.2 将入选问题写入考点导航

1. 在「已确认考点」章节，按[将入选问题写入导航的规则](/C:/Users/Administrator/.codex/skills/java-interview-doc-workflow/references/interview-topics.md:180)写入问题条目。每道追问放在直接引出它的问题下。对应的答题文档确定后，在条目后附上链接。

   文档拆分或重组后，核对读者能否从导航打开本次整理后的每篇文档。汇总等其他文档在导航中列出名称和链接。

2. 编写或复核考点导航时，单独读一遍每道题的条目，检查第一次接触项目的人能否看懂这道题要讲什么。条目中介绍业务流程时，用具体动作讲清各环节怎样衔接。需要提示答题范围时，另起一行，以「答题范围」开头。

   **示例** 迁移期间，业务继续写旧表，同时在旧库事务里保存同步任务。事务提交后，后台按任务把这次变更写到新表。历史迁移任务则分批搬运旧表里已有的流水。

   **答题范围** 讲清业务双写和后台迁移各负责哪些数据，以及两者怎样配合。

### 1.1.3 将各篇材料汇总到整理初稿

1. 把本次整理范围内各篇文档的内容汇总到本轮《整理初稿》中。逐篇对照原文：汇总中已有的相同内容只保留一份，原文里有而汇总里缺少的内容补进去，只在旧汇总中出现的内容也要保留。

   汇总时要保留答题内容、业务流程、技术说明、示例和来源，以及已确认的规则、待确认或待验证的事项和异议与分析。最后，在导航文档中加上指向这篇汇总文档的链接。

### 1.1.4 为每道问题确定答题文档和直接上级

1. 每篇答题文档围绕一个已确认的问题展开。按[1.2.1 安排文档章节](/C:/Users/Administrator/.codex/skills/java-interview-doc-workflow/references/interview-document-writing.md:29)，根据文档用途、当前问题和已有材料决定设置哪些章节。

2. 为每道已确认的主问题或追问安排答题文档时，按以下步骤处理。

   1. 对照题目和答题范围，查找主要回答这道题的现有文档。

   2. 找到合适的文档，就沿用该篇并补齐答案。只有找不到合适的文档时，才为这道题新建一篇。

   3. 如果原文还详细回答了某道已确认的追问，把这部分完整答案放入该追问的答题文档。原文保留理解本题所需的简要说明，并链接到追问文档。

   **示例** 原 013《批次启动锁设计》已经说明同一批次的请求怎样竞争锁、何时释放锁，就沿用 013 回答启动锁设计。“为什么选择 Redisson”确认为追问后，如果已有文档专门讲选型理由，就沿用该篇。只有缺少合适文档时，才新建这篇追问，并从 013 链接过去。

3. 每道已确认的追问应有一篇独立答题文档。已有文档主要回答该追问时，沿用该篇并补齐答案。找不到合适的文档时，为该追问新建一篇。将该追问直接承接的那道题的答题文档设为其直接主文档。

4. 每篇分文档只设一个直接主文档。答题文档也可以作为下一级追问的直接主文档。

5. 需要多篇共用的前提，可在各篇保留理解答案所需的简要说明。详细内容集中在对应文档，其他文档通过链接引用。

### 1.1.5 划分总述与追问各自要讲的内容

1. 追问独立成篇后，上一级文档保留回答自身问题所需的简短结论，并链接到追问文档。

   **功能总述的面试口述**

   1. 根据总述题和本篇已确认的考点组织口述，让听者仅凭这段话就能理解方案怎样解决主问题。

   2. 几项做法有先后依赖时，按实际顺序说明它们怎样配合。某个条件会改变主问题的答案时，在对应做法旁讲清这个条件。

   3. 独立追问的完整答案放在分文档。总述可以在文末用「相关追问」列出题目和链接，无需在口述中逐篇介绍。

   4. 口述中已经讲到的核心考点，如果有分文档详细说明，可以在对应段末链接到具体内容。同一链接列一次即可。

   **分文档的面试口述**

   1. 如果理解追问需要用到总述中的某个结论，先用一句话交代这个结论。

   2. 围绕追问比总述多问的内容，讲清具体做法和理由。

      **示例** 追问“任务重启后怎样恢复进度”时，讲清每个任务保存什么进度、重启后怎样读取，以及为什么要从这个位置继续。

## 1.2 安排文档顺序、编号和文件名

1. 在项目材料目录中每次新建 Markdown 文档前，按所在目录的编号顺序为每篇文档单独分配编号，并以 `三位编号_文档名称.md` 命名。此规则适用于所有新建的 Markdown 文档，包括初稿、候选问题清单、导航和汇总文档。无需拆分或重组时同样适用。

### 1.2.1 按阅读顺序分配文档编号

1. 分配编号前，先核对各组主问题的阅读顺序。逐组判断读者需要先了解哪些内容，把提供这些前提的文档组排在前面。涉及同一业务流程的文档组，按实际处理顺序排列。组内默认先排主文档，再依次排它的分文档和下级文档。

   **示例** 《改造计划》交代整体目标和实施阶段，《分库分表》展开其中一项设计，因此先排《改造计划》，再排《分库分表》。

   **示例** 核对新表与 ES 的数据时，需要知道一笔记录应当写入哪个月份的索引，以及用什么主键找到对应文档。因此先排讲解 ES 写入和索引设计的文档，再排《新表与 ES 增量校验》。这样也能讲清楚怎样发现应写入却缺失的记录。

2. 默认的主分顺序与内容依赖冲突时，在拆分方案中列明冲突和建议顺序，按用户确认的顺序编号。用户已指定顺序或起始编号时，按其要求执行。

3. 将已有和新增文档排在同一序列中，按确定的文档顺序分配连续的三位编号，不使用子编号。合并或移动文档后出现空号时，将后续文档按该顺序依次前移，补齐空号。`999` 文档保留原编号。需要调整本次授权范围外的文档时，先说明影响并请用户确认。

   **示例** 原 `013` 的内容并入 `012`，原 `013` 文件经确认移除后，原 `014` 改为 `013`，原 `015` 改为 `014`，后续文档依次前移。

4. 新增文档占用已有编号时，将原占用文档及后续受影响的文档按原顺序顺延。`999` 编号文档不参与顺延。顺延超出授权范围时，先说明影响并请用户确认。

   **示例** 在 `012` 和 `013` 之间新增一篇文档，新文档使用 `013`，原 `013` 顺延为 `014`，其后受影响的文档依次顺延。原 `999` 保持原编号。

### 1.2.2 按文档主题确定文件名

1. 分文档按 `三位编号_直接主文档主题_本篇主题.md` 命名。直接主文档主题取其目标文件名中去掉开头编号、下划线及 `.md` 后的完整名称。

   **示例** 「启动互斥」直接归属 `012_在线历史迁移_批次启动.md`，目标文件名为 `013_在线历史迁移_批次启动_启动互斥.md`。

2. 为技术选型题命名时，文件名中的「本篇主题」应写清项目在为哪类技术或方案做选择。具体选用了什么、为什么选它，在答案中说明。

   **示例** 项目为批次启动选择分布式锁实现，最终采用 Redisson 提供的 `RLock`。文件名写作 `025_批次启动锁设计_分布式锁选型.md`，面试题可以问「为什么选择 Redisson 的 `RLock` 实现批次启动锁？」

3. 多级拆分时，先确定上一级的目标文件名，再按直接主分关系逐层命名。

4. 每篇文档的一级标题与文件名一致，省略 `.md`。

5. 逐篇核对拆分范围内的命名，包括本次未改名的文档。用户指定的命名与主分命名规则冲突时，列出涉及的文件和冲突点，提交用户确认。

6. 候选问题清单需要注明材料范围时，将范围写在文档自身的编号和下划线之后，例如 `034_001–033候选问题清单.md`。

### 1.2.3 确定四类配套文档的名称和排列顺序

1. 最终交付时，同一整理目录中的四类配套文档各只保留最新一份。文件名和排列顺序如下。

   | 顺序 | 文件名格式 |
   |---|---|
   | 1 | `NNN_整理初稿.md` |
   | 2 | `NNN_面试考点_导航.md` |
   | 3 | `NNN_面试考点_已确认规则.md` |
   | 4 | `NNN_文档整理进度.md` |

2. 将这四份文档排在本次整理的其他文档之后。最终文档清单确定后，按表中顺序分配连续的三位编号。

   **示例** 最后一篇答题文档编号为 `062` 时，四份配套文档依次使用 `063` 至 `066`。后续新增答题文档时，按新的最终位置调整编号，并同步更新一级标题和相关引用。

## 1.3 编制拆分与重组方案，提交用户确认

1. 拟定拆分方案时，按[1.5.4 字符数统计](/C:/Users/Administrator/.codex/skills/java-interview-doc-workflow/references/interview-document-writing.md:109)的字符数统计口径评估面试口述篇幅。预计超过 300 字符时，检查是否有符合独立成篇条件的追问。继续拆分会影响答案完整性时，可以保留较长的口述。

2. 提交拆分或合并方案前，将原文中的内容逐项与本次整理后的其他文档对照，找出这些文档还没讲到的内容。确认方案的「内容去向」已逐项写明由哪篇文档承接。

3. 提交拆分方案时，按整理后的顺序列出每篇文档的编号、文件名和用途。答题文档注明题目和答题范围，追问文档同时注明其直接主文档。

4. 对拆分后预计口述仍超过 300 字符的答题文档，在提交确认的方案中逐篇列出拟用文件名、预计口述字符数和保留该篇幅的原因。

5. 对每道题，写清它想考什么，以及为什么值得单独用一篇文档来回答。如果题目来自项目材料，指出是根据哪份材料里的哪段内容拟的题。如果还引用了公开的相似面试题，给出原题出处，并指出两道题都问到了什么。项目材料和公开题都用到时，两处来源都写清楚。

   **示例** 「首次启动时，为什么要把批次状态更新和任务初始化放在同一个事务中？」承接「批次首次启动的流程是什么？」。

   - **题目来源** 标为「基于项目拟题」。项目方案把批次状态更新和任务初始化放在同一个事务中，由此提炼出这道题。
   - **考察内容** 候选人能否判断哪些操作需要一起提交或回滚，并说明划定这个事务边界的理由。
   - **独立成篇理由** 上一级题目讲首次启动的步骤。这道追问单独讲事务边界，重点解释为什么这两步需要放在同一个事务中。

6. 提交拆分方案时，写清以下两项。

   - **内容去向** 逐项写明要移动的内容及接收文档。接收文档为分文档时，写明它承接了直接主文档中的哪项内容。

   - **链接改动** 对每个受影响的链接，写明它位于哪篇文档，以及调整后应指向哪篇文档或哪个章节。

   **示例** 拟将《批次处理流程》中的「暂停与恢复」拆到《批次暂停与恢复》时，在方案中注明《迁移总览》里原来指向该小节的链接将改为指向新文档。

7. 用户确认拆分方案后，再按确认结果拆分、合并或重命名文档。

8. 需要调整已确认的拆分方案时，先向用户说明要改什么、为什么要改，以及会影响哪些文档和链接。等用户确认这些变更后，再按调整后的方案修改文件和链接。

   **示例** 用户已确认将「暂停与恢复」写成一篇。迁移正文时，发现「暂停」讲如何等待正在执行的任务结束，「恢复」讲如何从断点继续，适合分别成篇。此时先请用户确认是否同意拆成《批次暂停》和《批次恢复》，并说明原来指向「暂停」和「恢复」的链接将分别指向哪一篇。确认后，再拆分文档并更新链接。

## 1.4 按确认方案迁移内容并更新引用

1. 迁移内容时，一并保留理解结论所需的技术前提、适用范围、异常边界、示例和来源，并保留技术结论与来源的对应关系。相关的已确认规则、待确认或待验证事项也应随内容迁移。

2. 移除原文档中的重复内容前，先检查对应内容是否已完整写入目标文档。原文档仍承担导航职责时，保留必要的说明和链接。

3. 拆分后需要删除旧文档时，先在拆分方案中列明拟删除的文件。用户确认后，核对应保留的内容已完整迁入目标文档，将指向旧文件的引用更新到对应文档或章节，再删除旧文件。

   **示例** 《批次处理流程》的内容拆到了《批次启动》和《批次暂停与恢复》。如果你确认删除《批次处理流程》，原来指向其中「暂停与恢复」小节的链接，就要改到《批次暂停与恢复》的对应位置。

4. 文档拆分、合并、重命名或顺延编号后，同步更新受影响的考点导航、主分文档链接及其他关联引用。

5. 引用指向文档中的具体章节或行号时，按迁移后的位置更新。

## 1.5 核对重组结果并记录实际变更

1. 拆分完成后，对照已确认的拆分方案，检查原文中需要保留的内容是否完整写入对应文档。

   对照原文核对各篇正文中的技术结论、成立条件、适用范围和验证状态。

   **示例** 假设原文记录的是一项已确认的设计：首次启动批次时，启动事务提交成功后才调度迁移任务，实际运行效果尚未验证。拆分后的「任务调度」文档如果写成「批次状态更新后即可调度，流程已验证」，就需要补回「首次启动」和「事务提交成功」两个限定，并恢复原文的验证状态。

2. 对照已确认的拆分方案，检查每篇分文档是否归到正确的主文档下。

3. 对照已确认的拆分方案，检查每篇拆分后文档的文件名、一级标题和编号是否符合方案。

4. 对照已确认的拆分方案，检查考点导航是否列齐应收录的考点和文档，并逐题核对入选依据。

   引用公开面试题时，检查原题和出处是否支持所写的覆盖范围。题目由项目内容推导时，检查是否标为「基于项目拟题」。

5. 逐一检查拆分涉及的链接，确认应有的导航链接均已添加，链接文字与目标内容一致，并且指向实际存在的文档、对应章节或行号。「已确认考点」中的答题文档链接应指向拆分方案指定的文件。

   **示例** 原 `013` 顺延为 `014` 后，将考点导航及相关文档中指向原 `013` 的链接改为指向 `014`。如果正文也有移动，再核对链接指向的行号。

6. 完成拆分检查并修正发现的问题后，依照[逐篇整理与复核](/C:/Users/Administrator/.codex/skills/java-interview-doc-workflow/SKILL.md:56)章节的要求，按最终文档清单逐篇检查全文。

7. 本次整理结束或暂停后，在导航文档的「拆分记录」章节记录实际文件变更和已完成的检查结果。主分关系和尚待确认或验证的事项已有记录时，引用对应位置即可。
